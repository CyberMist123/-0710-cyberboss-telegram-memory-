P1-1: Telegram 429 retry_after 支持（方案，暂不修改）
======================================================================

问题: fetchJsonWithRetry 对所有非 200 响应统一 throw，
      不解析 429 响应体的 retry_after 字段。

涉及文件:
  - src/adapters/channel/telegram.js:225-241 (fetchJsonWithTimeout)
  - src/services/telegram-service.js:136-152 (同样的函数，双路径)

修改方案:
  1. 在 fetchJsonWithTimeout 中检查 response.status === 429
  2. 解析 response.json() 的 retry_after 字段
  3. 抛出自定义 TelegramRateLimitError(error, retryAfterMs)
  4. 在 fetchJsonWithRetry 中检查错误类型，用 retryAfter 作为延迟

伪代码:
  const response = await fetch(url, { ...options, signal: controller.signal });
  if (response.status === 429) {
    const body = await response.json().catch(() => ({}));
    throw new TelegramRateLimitError((body.retry_after || 5) * 1000);
  }
  if (!response.ok) {
    throw new Error(`telegram request failed: ${response.status}`);
  }

影响范围: 两个文件的 fetchJsonWithRetry 和 fetchJsonWithTimeout 均需修改。

P1-2: 指数退避重试（方案，暂不修改）
======================================================================

问题: 固定延迟数组 [1s, 3s, 6s]，只有 3 次重试。

涉及文件:
  - src/adapters/channel/telegram.js:21
  - src/services/telegram-service.js:12

修改方案:
  替换固定数组为指数退避 + jitter:

  const TELEGRAM_RETRY_BASE_MS = 1000;
  const TELEGRAM_RETRY_MAX_MS = 30000;
  const TELEGRAM_RETRY_MAX_ATTEMPTS = 5;

  for (let attempt = 0; attempt < TELEGRAM_RETRY_MAX_ATTEMPTS; attempt++) {
    const delay = Math.min(TELEGRAM_RETRY_BASE_MS * Math.pow(2, attempt), TELEGRAM_RETRY_MAX_MS);
    const jitter = Math.random() * 500;
    // 如果是 429，用 max(retryAfter, delay + jitter)
    await sleep(delay + jitter);
  }

  重试序列: ~1s → ~2s → ~4s → ~8s → ~16s
  429 时: 至少等待 retry_after 秒

P1-3: senderId/chatId 在群聊场景的正确性（分析）
======================================================================

当前 Telegram adapter 第 81 行过滤了非私聊消息:
  if (String(message.chat?.type || "") !== "private") return null;

因此当前不支持群聊。senderId(user.id) 和 chatId(chat.id) 在私聊中
永远相同，不存在混用问题。

如果未来支持群聊，需调整:
  - chat_id 用 message.chat.id（群 ID），不是 message.from.id（用户 ID）
  - senderId 用 message.from.id 用于白名单
  - replyTarget 用 chat.id
  - 白名单要支持 chat_id 和 user_id 两种模式

结论: 当前无风险，无需修改。

P1-5: Telegram service 与 adapter 双发送链路（分析）
======================================================================

两条路径职责不同:

  adapter (telegram.js)           service (telegram-service.js)
  ─────────────────────           ──────────────────────────
  主循环中 channelAdapter.send     MCP tool 调用
  userId 参数直接传                 resolveTelegramTarget() 解析目标
  ✅ 有 chunk 拆分                  ❌ 无 chunk 拆分
  ❌ 无 429 处理                    ❌ 无 429 处理

问题: service 路径没有长消息 chunk。
如果 MCP tool 返回长文本（超过 4096 字符），Telegram API 返回 400。

建议方案:
  1. 将 chunkReplyTextForTelegram 抽取为公共函数
  2. 让 service 的 sendText 也使用 chunk 循环
  3. 或将 service 的发送委托给 adapter
